## Phase 3: Dockerize the Full Stack

The project already has a [docker-compose.yml](file:///c:/Users/admin/Documents/Git/ML-Engineering-Projects/Projects/P3_Energy_Consumption_mlflow/docker-compose.yml) with Postgres, MinIO, MLflow, and a `serving` service. However, there are several issues to fix.

### 3.1 — Create a dedicated Dockerfile for the API

> [!IMPORTANT]
> Currently the `serving` service reuses `Dockerfile.mlflow`, whose `CMD` starts the MLflow server on port 5000. The `command:` override in docker-compose fixes this at runtime, but the image still EXPOSEs port 5000 and installs MLflow-server-specific dependencies. A separate Dockerfile is cleaner.

#### [NEW] Dockerfile.serving

```dockerfile
FROM python:3.11-slim
WORKDIR /app

RUN apt-get update && apt-get install -y --no-install-recommends \
    build-essential gcc libpq-dev curl \
 && rm -rf /var/lib/apt/lists/*

COPY Requirements.txt /app/Requirements.txt
RUN pip install --no-cache-dir -r /app/Requirements.txt

COPY src/ /app/src/
COPY artifacts/ /app/artifacts/

EXPOSE 8000

CMD ["uvicorn", "src.serving.api:app", "--host", "0.0.0.0", "--port", "8000", "--log-level", "info"]
```

Key differences from `Dockerfile.mlflow`:
- Only copies `src/` and `artifacts/` (not the entire repo)
- EXPOSEs 8000 instead of 5000
- CMD runs uvicorn, not mlflow server
- Adds `curl` for health checks

### 3.2 — Add MinIO bucket initialization

#### [NEW] init-scripts/create-bucket.sh

MinIO needs the `mlflow-artifacts` bucket created before MLflow can store artifacts. Add an init service:

```bash
#!/bin/bash
# Wait for MinIO to be ready, then create the bucket
mc alias set myminio http://minio:9000 minioadmin minioadmin
mc mb --ignore-existing myminio/mlflow-artifacts
echo "Bucket created successfully"
```

## User Review Required

> [!IMPORTANT]
> **MLflow tracking URI switch**: Phase 3.6 changes `mlflow_config.py` to prefer the `MLFLOW_TRACKING_URI` env var. This means in Docker, experiments will be tracked to Postgres (via the MLflow server), while locally they'll continue using the sqlite file. Existing local experiment history in `mlflow.db` **will not** be visible in the Dockerized MLflow. Is that acceptable, or do you want a migration strategy?

> [!WARNING]
> **Data in Docker**: The `.dockerignore` currently excludes `artifacts/`. This means the `serving` container won't have training/validation data baked into the image. The `Dockerfile.serving` above explicitly copies `artifacts/`, but you'd need to remove `artifacts/` from `.dockerignore` for that to work, or mount it as a volume. Which approach do you prefer?

## Open Questions

1. **Data volume strategy**: Should we bake `artifacts/data_ingested/` into the Docker image (simple, larger image ~100MB+), or mount it as a host volume (flexible, requires local data)?

2. **MinIO vs local storage**: For local development (Phase 2), the API currently uses local filesystem paths. In Docker (Phase 3), MLflow uses MinIO for artifact storage. Should the API also store predictions/models in MinIO when running in Docker, or keep using local filesystem paths inside the container?

3. **Scope of Phase 4**: The existing [ProjectSteps.md](file:///c:/Users/admin/Documents/Git/ML-Engineering-Projects/Projects/P3_Energy_Consumption_mlflow/ProjectSteps.md) mentions Kubernetes, Prometheus/Grafana, and A/B testing. Should Phase 4 include any of these, or keep it limited to tests + CI for now?
